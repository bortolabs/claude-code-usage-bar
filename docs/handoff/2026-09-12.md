## Contexto importante
- **O aviso de Node 20 na CI não é um prazo — a migração já aconteceu.** O log da 0.43.0 diz
  "This workflow is running with Node 24 **by default**": o release foi empacotado em Node 24 com
  as actions ainda em v4/v2, e funcionou. O handoff da S11 dizia que o pipeline pararia de
  empacotar; está errado. As actions estão 3 majors atrás (checkout v7, setup-node v7,
  gh-release v3), e `setup-node@v5` traz auto-cache por `packageManager` — breaking, mas inerte
  aqui porque o `cache: "npm"` é explícito. **Não mexer no `node-version: "20"` do `with:`**: esse
  é o Node que roda vitest/esbuild, outra coisa.
- **#32 — o que já foi descartado, para não refazer:** Keychain (`exec`, fora do processo,
  child não derruba host); módulo nativo (`dependencies: {}`); janela em epoch 0 (fallback de
  "5h" é `now - 5h`); OOM do ccusage (`maxBuffer` de 8MB); loop de `ready` no webview (`render()`
  faz `postMessage`, não re-seta HTML). **Suspeito:** o caminho síncrono
  `refreshCcusage → refreshStats → readTranscriptStats`, que aterrissa nos +4-5s dos crashes.
  Buraco na teoria: host bloqueado normalmente vira "unresponsive", não `crashed with code 5`.
- **`insightsEnabled: false` é o gate único desse caminho** (`extension.ts:942`) — por isso é o
  teste A/B decisivo pedido ao reporter.
